# 故障排查手册

## 1. 当前状态

项目已完成阶段 3，具有显式 State、受限 Loop、Tool Registry 和四个低风险工具。当前没有未解决的已确认代码缺陷；下面记录实际遇到的环境限制和统一排查方法。

## 2. 通用排查流程

### 第一步：确认范围

- 当前阶段和预期能力是什么？
- 问题发生在安装、启动、模型调用、解析、权限、工具、存储、检索还是评估？
- 是否只有真实模型失败，而 Fake LLM 测试正常？
- 是否涉及用户未提交改动或本地环境差异？

### 第二步：最小复现

- 使用最小输入重复问题；
- 暂时移除与问题无关的工具和数据，但不破坏用户文件；
- 记录执行命令、退出码、错误类别和必要日志；
- 不复制 API Key、认证头或敏感全文。

### 第三步：分层定位

```text
Environment
  -> Dependency/Import
  -> Configuration
  -> Provider/API
  -> Parsing/Validation
  -> Agent State/Loop
  -> Permission/Tool Execution
  -> Memory/Retrieval
  -> Evaluation/Reporting
```

先找到最早出现错误的层，不从最终错误消息直接猜测根因。

### 第四步：安全修复

- 优先修复根因，不用无限重试或放宽权限掩盖错误；
- 不运行破坏性 Git 或文件命令作为默认方案；
- 不覆盖用户未提交工作；
- 修复后添加失败案例和回归测试；
- 更新本文件和必要的 ADR。

## 3. 需要收集的信息

- 当前阶段、branch、commit/tag 和工作区状态；
- Python 与依赖管理工具版本；
- 锁文件是否与清单同步；
- 操作系统及必要环境差异；
- 已脱敏的配置变量名称，不能记录值；
- 最小输入、期望结果、实际结果和退出码；
- 失败所属 Run ID/Step ID（引入后）；
- 是否可在 Fake LLM、临时数据库或本地 MCP Server 中复现；
- 最近一次成功运行与发生变化的内容。

## 4. 常见问题分类

### 4.1 环境与依赖

可能表现：Python 版本不符、命令不存在、导入失败、锁文件漂移。

排查方向：

- 比较文档要求和实际版本；
- 确认使用了项目环境而非系统环境；
- 检查清单和锁文件是否同时更新；
- 从干净环境重建，而不是在旧环境不断补装未知依赖。

### 4.2 配置与 Secret

可能表现：变量缺失、凭据无效、错误日志泄露敏感内容。

排查方向：

- 只确认变量是否存在和格式是否合理，不打印真实值；
- 对照 `.env.example` 与配置校验代码；
- 区分缺少配置、认证失败和账号权限不足；
- 若可能泄漏，先轮换凭据，再调查历史和日志。

### 4.3 模型 API

可能表现：网络错误、超时、限流、模型不存在、Schema 不兼容。

排查方向：

- 查看厂商当前官方状态、文档和模型可用性；
- 区分可重试错误与永久配置错误；
- 检查 SDK、API 形态和模型能力是否匹配；
- 使用最小请求复现，不先修改 Agent Loop。

### 4.4 结构化输出

可能表现：JSON 无效、字段缺失、枚举值错误、额外参数。

排查方向：

- 保存已脱敏的原始响应；
- 检查 Prompt Schema 与程序 Schema 是否一致；
- 确认校验错误作为 Observation 或受控失败处理；
- 不通过跳过校验来“修复”。

### 4.5 Agent Loop

可能表现：无限循环、过早结束、完成状态与结果不一致。

排查方向：

- 检查每步前后 State 差异；
- 检查终止条件优先级、最大步数和错误分类；
- 使用脚本化响应复现状态序列；
- 用外部验证器检查完成结果。

### 4.6 Tool 与权限

可能表现：选错工具、参数错误、被错误拒绝或发生越权。

排查方向：

- 分开检查模型选择、Schema 校验、权限判定和实际执行；
- 检查规范化后的真实路径或命令参数；
- 不把权限拒绝改成自动允许；
- 检查超时、输出截断和审批记录。

### 4.7 Memory 与 RAG

可能表现：记住错误信息、查不到相关内容、引用不支持答案。

排查方向：

- 区分写入、持久化、查询、检索和生成层；
- 查看记忆或 Chunk 的来源和时间；
- 使用固定文档验证 Chunking 和 Top-K；
- 分别记录检索失败与生成失败。

### 4.8 MCP 与 Multi-Agent

可能表现：能力发现为空、连接失败、Schema 不一致、角色循环移交。

排查方向：

- 先用独立 Client/Server 验证 transport；
- 检查协议和 SDK 版本；
- 对比 Server Schema 与本地 Adapter；
- 检查全局步骤、交接和成本预算；
- 验证角色是否越过权限边界。

## 6. 当前已知问题

### TR-0001：当前环境没有 uv

- 首次出现阶段：阶段 0。
- 影响版本/commit：工作区尚未创建 Git commit。
- 状态：已解决。
- 表现：`command -v uv` 没有返回可执行文件。
- 最小复现：在当前环境查询 `uv` 命令。
- 期望结果：使用路线图建议的 uv 管理项目。
- 实际结果：uv 未安装。
- 根因：当前系统未提供 uv；这不是项目代码缺陷。
- 解决方法：按预先允许的备选方案使用 `.venv + pip`，固定直接依赖并生成 `requirements.lock`。
- 验证测试：editable 安装成功，阶段 3 当前 65 个测试通过。
- 安全影响：没有安装额外全局工具；`.venv` 已被 Git 忽略。
- 相关 ADR/阶段记录：[ADR-0002](decisions/ADR-0002-use-venv-and-pip.md)、[stage-00](stages/stage-00.md)。
- 仍存在的限制：若未来改用 uv，必须统一迁移锁文件和文档命令。

### TR-0002：测试意外发现父目录 `.env`

- 首次出现阶段：阶段 0，切换硅基流动配置时。
- 影响版本/commit：工作区尚未创建 Git commit。
- 状态：已解决。
- 表现：在临时子目录测试“缺少 API Key”时没有抛出配置错误。
- 根因：`python-dotenv` 的默认查找会沿调用位置向父目录寻找 `.env`，从而加载项目中的本地配置。
- 解决方法：显式使用 `load_dotenv(dotenv_path=".env")`，只读取当前工作目录下的配置。
- 验证测试：新增“不得搜索父目录”回归测试；测试不输出 Secret，也不调用网络。
- 安全影响：旧行为可能让测试读取本不属于其隔离目录的凭据；本次没有输出 Key或发送 API 请求。
- 相关阶段记录：[stage-00](stages/stage-00.md)。

### JSON 决策无法校验

- 表现：CLI 以 `unrecoverable_error` 终止，并提示模型决策不是有效的约定 JSON。
- 原因：模型返回被截断、不是 JSON、字段名错误，或 `complete`/`fail` 缺少必填结果字段。
- 排查：确认模型名有效、服务正常且返回完整 JSON；保留合理 `max_tokens`，不要删除 Pydantic 校验。阶段 1 使用 JSON Mode；阶段 2 的工具启用请求遵循 ADR-0005，不与自动 Function Calling 同时开启 JSON Mode。
- 当前策略：安全终止且不自动重试。重试和退避属于后续工程可靠性阶段。

### TR-0003：JSON Mode 与自动 Function Calling 组合未产生工具调用

- 首次出现阶段：阶段 2 真实模型验收。
- 影响模型：当时配置的 `deepseek-ai/DeepSeek-V4-Flash`。
- 状态：已解决并保留架构记录。
- 表现：同时发送 `tools`、`tool_choice=auto` 和 `response_format=json_object` 时，请求成功，但模型返回缺少必要字段的普通 JSON，`tool_calls` 为 `None`。
- 期望结果：模型为算术任务返回原生 Calculator 调用。
- 根因：依据重复对照请求，当前模型/服务组合在这组参数下没有选择工具；这是实测兼容性行为，未推断为所有模型的通用限制。
- 解决方法：工具启用请求移除 `response_format`，保留 Function Calling 和 Pydantic 文本决策校验。
- 验证测试：同一目标随后返回 `finish_reason=tool_calls`；完整 CLI 两步闭环成功。
- 安全影响：没有放宽工具名称、参数或执行校验；格式错误仍会安全终止。
- 相关 ADR/阶段记录：[ADR-0005](decisions/ADR-0005-native-function-calling-with-single-calculator.md)、[stage-02](stages/stage-02.md)。

### TR-0004：直接解析 JSON Decimal 导致长小数先被浮点截短

- 首次出现阶段：阶段 2 数值边界测试。
- 状态：已解决。
- 表现：51 位小数通过 `model_validate_json` 后只剩约 16 位，导致精度和小数位限制与原始 JSON 不一致。
- 根因：该解析路径先把 JSON number 转为二进制浮点，再构造 Decimal；原始十进制词法已经丢失。
- 解决方法：使用 `json.loads(parse_float=Decimal, parse_int=Decimal)` 保留原始数值，再用 Pydantic 和显式位数验证器校验；同时拒绝非标准 JSON 数字。
- 验证测试：`0.1 + 0.2` 精确得到 `0.3`；40 位整数乘法精确；超过 100 位或 50 位小数被拒绝。
- 安全影响：限制超长数值，避免异常大的计算和输出；不解析或执行任何表达式。
- 相关阶段记录：[stage-02](stages/stage-02.md)。

### 文件读取工具返回拒绝

- 检查输入是否为当前启动目录下的相对路径，且后缀为 `.txt` 或 `.md`。
- 隐藏路径、绝对路径、`..`、符号链接逃逸、非 UTF-8、非普通文件和超过 64 KiB 均会拒绝。
- 当前安全读取依赖 POSIX `O_NOFOLLOW` 和相对目录描述符；缺少这些原语的平台会明确拒绝，不会退回到存在竞态窗口的路径式读取。
- 不要通过放宽边界读取 `.env`；需要其他文件能力时应在后续阶段先定义权限和审批。

### TR-0005：模型能力声明与执行能力可能分叉

- 首次出现阶段：阶段 3 完成后的代码审查。
- 影响版本/commit：原 `stage-03` 提交 `ac86c4a`。
- 状态：已解决。
- 表现：Client 与 Runner 都能静默创建默认 Registry，或调用者只给一端传入自定义能力，导致模型看到的工具与 Runner 可执行工具不同。
- 最小复现：Client 只收到 Echo definition，Runner 使用默认四工具。
- 根因：能力声明和执行各自持有可独立配置的来源，单一 Registry 只由 CLI 惯例保证。
- 解决方法：Runner 持有唯一 Registry，每次决策将同一实例传给 DecisionMaker，Client 不再保存或创建独立工具定义。
- 验证测试：自定义 Echo Tool 的 Runner + Fake LLM 闭环断言两次决策与执行均使用同一 Registry。
- 安全影响：避免模型声明、Registry 和后续 Policy 出现能力漂移。
- 相关 ADR/阶段记录：[ADR-0006](decisions/ADR-0006-tool-registry-and-low-risk-builtins.md)、[stage-03](stages/stage-03.md)。

### TR-0006：只读文件检查与读取存在竞态窗口

- 首次出现阶段：阶段 3 完成后的代码审查。
- 影响版本/commit：原 `stage-03` 提交 `ac86c4a`。
- 状态：已解决（支持安全打开原语的 POSIX 平台）；其他平台安全拒绝。
- 表现：旧实现依次 `resolve/stat/read_text`，路径可能在检查后被替换，文件也可能在大小检查后增长。
- 根因：检查路径指向的对象后，按路径名重新打开；实际使用对象并非必然是已检查对象，读取也没有硬上限。
- 解决方法：从工作区目录描述符逐级使用 `O_NOFOLLOW` 打开；对最终文件描述符执行 `fstat`；最多读取上限加一字节并拒绝超限内容。
- 验证测试：符号链接拒绝、大小边界和“描述符检查显示未超限但实际内容超限”模型测试通过。
- 安全影响：降低不可信或并发工作区中的路径替换、符号链接和文件增长风险。
- 相关 ADR/阶段记录：[ADR-0006](decisions/ADR-0006-tool-registry-and-low-risk-builtins.md)、[stage-03](stages/stage-03.md)。
