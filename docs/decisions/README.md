# 架构决策记录（ADR）

## 1. 目的

ADR 用于记录对项目具有长期影响、存在合理备选并需要解释权衡的决定。它回答“为什么这样做”，而不是替代代码、阶段记录或操作手册。

当前使用硅基流动 Chat Completions API，见 ADR-0003；当前环境使用 venv + pip，见 ADR-0002。显式状态见 ADR-0004，原生 Function Calling 见 ADR-0005，统一 Tool Registry 和低风险工具见 ADR-0006。向量存储、MCP 和后续框架方案仍是建议或待确认项。

## 2. 何时创建 ADR

适合记录：

- 模型供应商、主要 API 形态或 Provider 边界；
- uv 与其他依赖管理方案的选择；
- 同步与异步运行模型；
- State、Tool、Memory 或 Agent Runtime 的长期接口；
- 数据库、Embedding、向量存储和 MCP transport；
- 权限、审批、日志、Checkpoint 或部署策略；
- 引入或拒绝成熟 Agent 框架。

通常不需要 ADR：

- 小型 Bug 修复；
- 局部重命名或格式调整；
- 没有备选方案的需求约束；
- 只在单个阶段临时使用且不会形成长期约束的细节。

## 3. 命名规则

```text
ADR-0001-short-kebab-case-title.md
ADR-0002-another-decision.md
```

编号只递增，不复用。文件使用中文正文，标题可使用清晰中文。

## 4. 状态

- 提议：正在讨论，不能当作既定事实。
- 已接受：决定生效，代码和其他文档应与之一致。
- 已拒绝：明确未采用，保留理由。
- 已取代：由新的 ADR 替代，双向链接。
- 已废弃：不再适用但没有直接替代。

只有学习者明确确认或当前阶段授权范围内具有充分证据的决定才能标记“已接受”。重大成本、安全或供应商选择应优先由学习者确认。

## 6. ADR 维护规则

- 已接受 ADR 不直接改写历史结论；方向改变时创建新 ADR 并标记取代关系。
- 文档中的当前架构必须符合所有有效 ADR。
- SDK 或协议发生变化不自动使 ADR 失效，应评估其影响。
- ADR 不得包含 Secret 或敏感内部地址。
- 阶段记录应链接本阶段新增或受影响的 ADR。
