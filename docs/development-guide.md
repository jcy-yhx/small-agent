# 开发指南

## 1. 开发原则

- 只实施学习者明确确认的当前阶段。
- 基于上一阶段增量修改，不无解释地整体重写。
- 每个阶段只引入当前问题所需的主要抽象。
- 保持同步、简单和可调试；异步必须有真实需求。
- 优先自己实现核心 Agent 逻辑，成熟框架延后比较。
- 先保证离线确定性测试，再进行真实模型手动验收。
- 不自动提交、打 tag、推送或创建远程仓库。

## 2. 开始任何阶段前

1. 确认学习者已明确授权该阶段。
2. 阅读最近阶段记录、阶段规范和当前架构。
3. 检查 Git 当前分支、commit 和未提交变更。
4. 运行上一阶段的自动化测试并记录基线。
5. 核对当前 Python、依赖管理工具和锁文件状态。
6. 若涉及 SDK、API、模型、价格或协议，查阅当时官方文档。
7. 列出本阶段新增、修改和可能删除的文件。
8. 明确正常、边界、失败案例与通过标准。
9. 明确本阶段不会实现的后续能力。

## 3. Python 与项目环境

### 建议方案

- Python 3.11 或更高版本；
- 使用 uv 创建环境、管理直接依赖和锁定传递依赖；
- 使用 `src` 布局和类型注解；
- 使用 pytest。

### 备选方案

若运行环境不支持 uv，可使用 venv + pip，并选择可复现的锁定方式。切换必须记录 ADR 或阶段决策，更新所有运行说明，不能同时维护互相冲突的命令。

### 当前状态

当前系统没有 uv，阶段 0 已按 [ADR-0002](decisions/ADR-0002-use-venv-and-pip.md) 采用 venv + pip：

- 本地环境目录：`.venv`，不得提交；
- 直接依赖与开发依赖：`pyproject.toml`；
- 完整验证版本：`requirements.lock`；
- Python 验证版本：3.14.4，项目最低要求仍为 3.11。

常规开发使用 editable 安装；严格复现使用锁文件后再以 `--no-deps` 安装本项目。命令以根目录 README 为准。

## 4. 依赖管理与锁定规范

- 只在当前阶段确有用途时增加依赖。
- 直接依赖必须出现在项目清单，传递依赖由锁文件记录。
- 增加、删除或升级依赖时必须同步锁文件。
- 禁止只修改环境、不修改清单或锁文件。
- 不手工编辑锁文件，除非所选工具官方流程明确要求。
- 阶段记录必须说明依赖变化、原因和兼容性影响。
- 安装前核对包名，降低依赖混淆风险。
- 重要升级先阅读官方变更和弃用说明，再运行全部测试。
- 新环境必须能仅凭仓库清单与锁文件重建。

## 5. 环境变量规范

### 文件职责

- `.env.example`：只保存变量名称、安全示例和注释，可以提交。
- `.env`：保存本机真实值，不得提交。
- 测试环境：使用测试注入或假值，不读取个人真实 Key。

### 命名与校验

- 使用大写蛇形命名，如 `MODEL_API_KEY`；具体供应商名称待选型后确定。
- 每个变量必须说明是否必需、默认值、格式和敏感级别。
- 启动时集中校验，缺失时给出变量名和修复方向，但不输出真实值。
- 不把 Secret 作为 CLI 参数，避免进入 shell 历史和进程列表。
- 不在 Prompt、Trace、异常、测试快照或评估报告中写入 Secret。

### 计划中的变量类别

当前已使用：

- `SILICONFLOW_API_KEY`：必填 Secret，无默认值；
- `SILICONFLOW_MODEL`：可选，默认 `deepseek-ai/DeepSeek-V4-Flash`；
- `SILICONFLOW_BASE_URL`：可选，默认 `https://api.siliconflow.cn/v1`。
- `AGENT_MAX_STEPS`：可选整数，范围 1～10，默认 3，不是 Secret。

为了兼容已经创建的本地配置，程序也接受 `OPENAI_API_KEY` 与 `OPENAI_MODEL`，但新配置应使用 `SILICONFLOW_*`。配置加载只读取当前工作目录的 `.env`，不得向父目录搜索 Secret。

后续计划中的变量类别：

- 可选 API Base URL；
- 日志级别和运行环境；
- Agent 超时、Token 与成本预算；
- 数据库、知识库和工作区路径；
- MCP Server 配置。

## 6. 代码组织规范

- 业务入口保持薄，只负责读取输入、构造依赖和展示结果。
- 核心逻辑通过函数或小型类暴露，避免隐藏在 CLI 中。
- 外部 I/O 与纯状态转换分离，便于测试。
- Schema 代表程序边界，不直接信任模型返回的字典。
- 公共接口尽量提供完整类型注解。
- 错误按调用、解析、校验、权限、执行、超时和预算分类。
- 不使用裸 `except` 吞掉错误。
- 删除或替换旧接口时说明迁移方式并更新测试。

### 当前工具规范

- 当前只允许默认 Registry 中明确注册的四个低风险 Tool，不得动态执行 Python 函数；
- Function Calling 只是调用意图，只有 `AgentRunner` 生成的 `ToolObservation(success=true)` 代表执行成功；
- Calculator 参数由 Pydantic 校验，禁止 `eval`、`exec` 和动态 import；
- 操作数最多 100 位、最多 50 位小数，只允许加、减、乘、除；
- 工具失败作为 Observation 返回循环，不伪装成结果；
- 新工具必须继承 `BaseTool`，提供 Schema 和确定性测试，经 Registry 注册；不得修改 Agent Loop 增加名称分支。
- `read_text_file` 只允许工作区内非隐藏 `.txt/.md`、UTF-8、最大 64 KiB；真实 `.env` 永远不属于可读范围。

## 7. 日志与可观察记录

### 早期阶段

早期只记录理解当前执行所必需的信息，避免先搭建复杂日志系统：

- 事件类型；
- 当前步骤；
- 决策类型和行动名称；
- 已脱敏的参数；
- Observation 摘要；
- 是否继续和终止原因；
- 错误类别。

### 后期阶段

生产化阶段再统一加入：

- 时间戳、Run ID、Step ID；
- 模型、Token、估算成本和延迟；
- 重试次数和预算剩余量；
- 工具、权限决策和人工审批结果；
- Checkpoint 与恢复信息。

日志禁止包含 API Key、认证头、完整敏感文档、未脱敏个人信息和隐藏思维链。输出长度必须受限。

## 8. 测试流程

- 单元测试默认不得联网，也不得产生真实副作用。
- 使用 Fake LLM 或脚本化响应测试状态转换。
- 工具选择、工具执行和最终回答分层测试。
- 每次修改先运行最相关测试，再运行完整回归测试。
- 非确定性在线测试与确定性测试分开标记，不阻塞日常离线开发，除非阶段验收明确要求。
- 具体分层和指标见 `testing-strategy.md`。

## 9. Git 记录规范

- 每阶段建议对应一个清晰 commit，如 `stage-00-minimal-chat`。
- Tag 建议使用 `stage-00`、`stage-01` 等；是否创建由学习者确认。
- 未经明确要求不得自动 commit、tag、push 或创建远程仓库。
- 阶段记录必须写明 commit SHA 和 tag；不存在时写“未创建”。
- 提交前检查 Secret、生成数据、大型日志和本机数据库未被纳入。
- 不通过重写共享历史来修复普通问题。
- 保留用户现有未提交改动，不擅自丢弃。

## 10. 文档同步工作流

每阶段实施完成、验收通过后，按顺序更新：

1. `architecture.md`：当前目录、组件、数据流和限制。
2. `stage-specification.md`：状态、日期和验收摘要。
3. `stages/stage-XX.md`：完整实施记录。
4. `troubleshooting.md`：新增的真实故障及解决办法。
5. `decisions/ADR-XXXX-*.md`：重要技术决策。
6. `README.md`：当前里程碑和恢复入口。
7. 其他因实现事实发生变化而受影响的文档。

完成后执行一致性检查：

- 文档提到的路径真实存在；
- 示例命令与所选工具一致；
- 配置名称与代码一致；
- 阶段状态与测试结果一致；
- 当前架构没有混入未来模块；
- Git commit/tag 记录准确；
- 链接有效，术语使用一致。

## 11. 故障处理

遇到故障时按 `troubleshooting.md` 的流程收集证据。修复应遵守：

- 先复现、分类和缩小范围，再修改；
- 不用删除用户数据或重置仓库作为默认修复；
- 不通过无限重试掩盖根因；
- 修复后添加回归测试；
- 将具有复用价值的问题写入故障文档；
- 若修复改变长期架构选择，新增 ADR。

## 12. 阶段结束条件

只有代码、测试、手动验收、文档和能力边界均完成，当前阶段才能标记为“已完成”。随后必须停止，等待下一阶段的明确确认。
