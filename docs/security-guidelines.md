# 安全指南

## 1. 安全目标

Agent 会把不可信模型输出转化为潜在外部操作，因此安全控制必须由程序执行。目标是在整个课程中保持最小权限、明确授权、可审计、可终止和可恢复。

当前项目尚未实现任何工具或外部操作。本规范是后续阶段的强制边界，不表示相应控制已经实现。

## 2. 信任边界

以下输入默认不可信：

- 用户输入；
- 模型文本、结构化输出和工具调用参数；
- 网页、文件、RAG 文档和检索片段；
- Tool Observation；
- Long-term Memory 中的历史数据；
- MCP Server 描述、Schema、资源和执行结果；
- 其他 Agent 的消息；
- 日志或评估数据中的可执行内容。

不可信不等于一律拒绝，而是必须校验、限制和按来源处理。

## 3. 核心执行原则

```text
模型提出意图
  -> Schema 校验
  -> 语义校验
  -> 权限检查
  -> 预算检查
  -> 必要时人工确认
  -> 受限执行
  -> 结果截断与清洗
  -> Observation
```

- 模型不能自行授予权限。
- Prompt 里的“不要做危险操作”不是安全边界。
- 权限应小于或等于任务实际需要。
- 默认拒绝未定义工具、未知参数和越界资源。
- 高风险操作在执行前确认，而不是执行后告知。

## 4. Secret 与配置

- 真实 Key 只存在于本机安全环境或未来采用的 Secret Manager。
- `.env` 必须被 Git 忽略；`.env.example` 只能包含占位符。
- 不在代码、测试夹具、文档、截图、日志、Trace 或异常中输出 Secret。
- HTTP 认证头和连接字符串必须脱敏。
- 不把 Secret 放入模型 Prompt 或工具 Observation。
- 发现 Secret 进入 Git 历史时，不只删除当前文件；应停止并制定吊销与历史处理方案。
- 交接项目时只提供变量名称，不提供真实值。

## 5. 文件系统安全

文件工具引入后必须：

- 绑定单一、明确、非根目录的工作区；
- 对输入路径进行规范化并验证最终目标仍在工作区；
- 防止 `..`、绝对路径、符号链接和竞态绕过；
- 读写分别授权，默认只读；
- 限制文件类型、单文件大小和总输出长度；
- 拒绝设备文件、套接字、密钥目录和版本控制敏感区；
- 覆盖或删除前要求更高等级确认，并优先可恢复操作；
- 在日志中记录脱敏后的目标、动作和结果。

## 6. Shell 安全

Shell 工具引入后必须：

- 使用命令和参数允许列表，而不是字符串黑名单；
- 优先不经过 shell 的参数数组执行方式；
- 禁止把模型文本直接拼接为命令；
- 限制工作目录、环境变量、执行时间和输出大小；
- 不继承非必要凭据和网络权限；
- 拒绝提权、持久后台进程、交互命令和破坏性操作；
- 超时后可靠终止子进程；
- 对副作用和重试设计幂等或去重策略。

## 7. 网络安全

若后续引入网络工具：

- 默认禁止，按工具和目标域明确授权；
- 限制协议、方法、重定向次数、超时和响应大小；
- 防止访问本机、内网、云元数据和非预期地址；
- 不自动上传本地文件、Memory、Prompt 或 Secret；
- 把远程内容当数据，不执行其中的指令；
- 记录目标域和结果摘要，不记录认证材料；
- 下载内容在进一步解析或执行前重新校验。

## 8. Prompt Injection 与工具注入

- System Prompt 不能覆盖程序权限边界。
- RAG 文档中的“忽略之前指令”只视为文档内容。
- 工具描述和 MCP 能力元数据也必须来自可信配置或经过审核。
- 模型选择工具后仍需独立检查当前用户、任务和参数是否获准。
- Observation 回传模型前进行长度限制、数据分类和必要脱敏。
- 安全测试应包含直接、间接和跨工具注入案例。

## 9. Memory 与 RAG 安全

- Long-term Memory 默认只保存用户明确要求记住的信息，自动写入策略需单独确认。
- 每条记忆记录来源、时间和可删除标识。
- 支持更正、过期和删除，不能将错误记忆永久固化。
- 不把全部聊天历史默认保存为记忆。
- RAG 文档记录来源和信任等级，检索相关性不代表内容可信。
- 回答应区分模型知识与检索证据，并在要求时展示来源。
- 删除源文档时考虑派生 Chunk、Embedding 和缓存的生命周期。

## 10. MCP 与 Multi-Agent 安全

- MCP 标准化连接，不提供自动信任。
- 每个 Server 需要明确来源、transport、能力范围和凭据边界。
- Server 返回的工具 Schema 与结果仍要校验和限制。
- 本地 Tool 与 MCP Tool 应经过相同的权限、预算和审计网关。
- Multi-Agent 角色不能通过转交任务提升权限。
- 共享状态按最小需要暴露，避免 Secret 和隐私在角色间扩散。
- 使用全局步骤、成本、时间和交接次数上限防止循环协作。

## 11. Human-in-the-loop

人工确认请求必须展示：

- 将执行的具体动作；
- 目标资源；
- 关键参数；
- 可能的副作用和可恢复性；
- 为什么需要该操作；
- 允许、拒绝后的行为。

确认只对展示的单次具体操作有效，不应成为长期无限授权。输入不完整、目标变化或参数变化后应重新确认。

## 12. 预算与拒绝服务防护

逐阶段加入并最终统一管理：

- 最大 Agent 步数；
- 单步和总运行超时；
- 每类错误最大重试次数与退避；
- 最大 Prompt、Observation 和日志长度；
- 输入/输出 Token 预算；
- 成本预算；
- 并发与工具调用频率；
- MCP/Multi-Agent 交接上限。

达到预算应进入明确终止状态，不能静默扩大预算。

## 13. 安全事件响应

发现疑似 Secret 泄漏、越权执行或数据破坏时：

1. 立即停止相关运行，保留最小必要证据。
2. 不在普通日志或聊天中继续传播敏感内容。
3. 确认影响范围和实际副作用。
4. 吊销或轮换可能暴露的凭据。
5. 使用可恢复方式隔离受影响数据。
6. 增加回归测试并修复代码级边界。
7. 更新故障文档；涉及长期策略时新增 ADR。
8. 如实说明哪些内容可恢复、哪些不能。

## 14. 阶段安全门禁

每阶段结束前检查：

- 新增输入是否被视为不可信；
- 新增权限是否为完成任务的最小范围；
- 是否存在绕过校验或审批的路径；
- 日志、错误和测试是否泄露 Secret；
- 超时、输出和循环是否有界；
- 安全失败是否默认拒绝；
- 相关安全案例是否自动化；
- 当前 Demo 与生产系统差距是否如实说明。
