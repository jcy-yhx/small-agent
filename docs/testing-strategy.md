# 测试与评估策略

## 1. 目标

测试用于验证确定性规则，评估用于衡量非确定性 Agent 行为。两者共同回答：系统是否按设计工作、是否真正完成任务、是否越过安全边界，以及修改是否造成回归。

阶段 0 建立了单次生成测试基线。阶段 1 已扩展到 25 个离线测试，覆盖 State Schema、结构化 JSON 决策、循环、五类终止原因、CLI 和阶段 0 回归；并使用硅基流动 `deepseek-ai/DeepSeek-V4-Flash` 完成真实模型在线验收。

## 2. 每阶段最低测试要求

每个阶段必须至少包含：

1. 一个正常案例；
2. 一个边界案例；
3. 一个失败案例；
4. 一个不依赖真实模型的自动化测试；
5. 一个手动验收步骤；
6. 可从外部观察的完成标准；
7. 对上一阶段的回归测试。

没有测试和文档同步的阶段只能标记“待验收”，不能标记“已完成”。

## 3. 测试分层

### 3.1 单元测试

用于纯逻辑和明确边界：

- State 转换和终止判断；
- Pydantic/Schema 校验；
- Tool Registry；
- 权限、路径和预算策略；
- Context 裁剪与排序；
- Memory CRUD；
- Chunking 和检索评分；
- 计划状态迁移；
- 指标计算。

要求快速、离线、无真实副作用。

### 3.2 组件测试

验证一个模块与其直接边界：

- LLM Client 与 Fake Transport；
- 工具调用解析与工具执行器；
- SQLite Store 与临时数据库；
- Retriever 与固定本地语料；
- MCP Client 与本地测试 Server。

### 3.3 集成测试

验证多个组件形成的闭环：

- Decide → Tool Call → Execute → Observation → Final；
- Context Builder → Retrieval → Model Input；
- Planner → Executor → Replanner；
- MCP 能力发现与调用；
- Multi-Agent 角色交接。

集成测试默认使用脚本化模型响应，以保证可复现。

### 3.4 安全测试

至少覆盖：

- 路径穿越、绝对路径和符号链接逃逸；
- Shell 元字符、命令拼接和不在允许列表的程序；
- 未授权副作用和审批拒绝；
- Secret 脱敏；
- Prompt/Tool/RAG 注入样本；
- 超时、输出截断、步骤和成本预算；
- 重试导致的重复副作用；
- 不可信 MCP Server 返回内容。

### 3.5 在线烟雾测试

调用真实模型的测试用于人工验收或受控评估：

- 与离线测试分离标记；
- 默认不在普通单元测试中运行；
- 需要显式环境配置；
- 设置请求次数、Token、成本和超时上限；
- 不把真实 API Key 写入测试输出；
- 失败时区分账号、网络、限流、模型变化和 Agent 逻辑。

### 3.6 回归评估

阶段 11 将前面累计的案例整理为 Golden Dataset，但数据从阶段 0 开始持续积累。每个已确认 Bug 都应尽量形成回归案例。

## 4. Fake LLM 规范

Fake LLM 或脚本化响应应：

- 接受与真实 Client 足够相似的输入边界；
- 按调用顺序返回预设文本、结构化结果或错误；
- 能记录收到的消息和工具 Schema，供断言使用；
- 能模拟格式错误、超时、限流和空响应；
- 不尝试模拟模型智能，只验证程序控制流。

不要用 Mock 掩盖所有内部细节；优先在稳定边界替换外部模型调用。

## 5. 测试数据规范

- 测试数据必须小、明确、可审查。
- 不使用真实 Secret、个人隐私或受限制数据。
- RAG 测试文档应有稳定 ID、来源和已知相关问题。
- Golden Dataset 的每个案例需记录目标、输入、期望约束和评分方式。
- 非唯一答案不应依赖字符串完全相等。
- 测试数据库、索引和工作区使用隔离临时目录。
- 测试结束后只清理自身创建的明确目标，不操作用户目录。

## 6. 逐步增加的指标

| 指标 | 首次关注阶段 | 说明 |
|---|---:|---|
| 输出格式正确率 | 1 | 结构化决策可被 Schema 接受的比例 |
| 工具选择正确率 | 2～3 | 是否调用正确工具或正确选择不调用 |
| 工具参数正确率 | 2 | 参数语法和语义是否正确 |
| 任务完成率 | 1 起步，11 系统化 | 依据外部结果或验证器判断 |
| 循环步数 | 1 | 完成、失败和超预算的步数分布 |
| 错误恢复率 | 2+ | 可恢复错误后继续完成的比例 |
| 安全策略命中率 | 4 | 应拒绝案例被正确拒绝的比例 |
| 检索 Recall@K/命中率 | 7 | 相关 Chunk 是否进入 Top-K |
| 来源可靠性 | 7 | 回答声明是否受给定来源支持 |
| Token 消耗 | 5+ | 输入、输出和总使用量 |
| 执行时间 | 0+ | 调用、步骤和总运行延迟 |
| 估算成本 | 5+ | 依据明确价格快照计算并注明日期 |
| 协作收益 | 10 | Multi-Agent 相对单 Agent 的质量、成本与延迟 |

## 7. 任务完成判定

优先级从高到低：

1. 确定性验证器：计算结果、文件状态、数据库记录或测试结果。
2. 明确规则评分：Schema、关键词约束、来源匹配、步骤状态。
3. 人工评审：适合开放式质量和教学理解。
4. LLM-as-a-Judge：仅作为辅助，并记录模型、Prompt、重复次数和偏差风险。

模型输出“任务已完成”本身不构成完成证据。

## 8. 非确定性处理

- 对模型输出设置低随机性不能替代评估。
- 固定模型版本、Prompt、工具 Schema 和数据集版本，或记录其变化。
- 重要指标运行多次并报告分布，不只报告最好结果。
- 对失败进行分类，避免把网络故障算成推理错误。
- 任何阈值必须在阶段记录中说明依据。
- 模型或 Prompt 变更后运行回归评估并比较基线。

## 9. 阶段质量门禁

标记阶段完成前必须确认：

- 本阶段特定测试全部通过；
- 以前阶段的回归测试通过；
- 没有依赖真实网络的默认单元测试；
- 手动验收已记录日期和结果；
- 已知失败没有被静默忽略；
- 测试未泄露 Secret 或污染用户文件；
- 阶段记录写明运行范围、结果和未覆盖风险。

## 10. 阶段 11 的系统化产物

计划形成：

- 版本化 Golden Dataset；
- 统一 Evaluation Runner；
- 工具、RAG、规划、安全、成本和延迟指标；
- 机器可读与人可读报告；
- 基线和回归阈值；
- 可追溯到 Run/Step 的失败样本；
- LLM Judge 与人工抽查的组合策略。

这些产物尚未实现。
